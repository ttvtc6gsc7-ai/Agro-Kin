Guide de lecture du projet

Comprendre le code de RoboAgri Kin

Structure, parcours des données, rôle des pages et limites actuelles de cette interface front-end.

À retenir : cette version est une démonstration. Les missions ne sont pas envoyées à un robot ou à un ESP32.

Technologies : HTML5, CSS3 et JavaScript, avec Bootstrap Icons et Plotly chargés depuis des CDN.

1. Démarrer l’application

Ouvrir index.html dans un navigateur pour voir la page d’accueil, puis choisir Découvrir l’application pour ouvrir dashboard.html. Les autres pages peuvent aussi être ouvertes directement.

Une connexion Internet est nécessaire pour charger Bootstrap, Bootstrap Icons et Plotly depuis leurs CDN. La photographie de l’accueil est hébergée sur le site FarmDroid.

3. Page d’accueil

index.html contient l’en-tête, les liens vers les sections, la photographie FarmDroid créditée, les quatre cartes de fonctionnalités, la présentation de la mission et le pied de page. Les boutons Découvrir l’application ouvrent dashboard.html, séparé de l’accueil pour préserver sa fonction de supervision.

js/landing.js gère le menu mobile, l’année du pied de page et l’apparition des sections au défilement avec IntersectionObserver. Si l’API du navigateur n’est pas disponible, les sections sont affichées directement.

L’écran de bienvenue affiche un robot illustré en SVG qui fait coucou avec son bras. L’animation est définie dans css/amelioration.css et reste désactivée automatiquement lorsque le navigateur utilise prefers-reduced-motion. Le script js/accueil.js affiche ou masque cet écran avec le bouton Entrer et le bouton Retour.

4. Tableau de bord et navigation

Chaque page de supervision charge dans cet ordre js/data.js, js/api.js, puis js/app.js. Le HTML indique la vue à rendre avec body[data-page]. Le tableau de bord utilise data-page="index" ; cela ne fait pas de index.html la page de tableau de bord.

app.js crée le menu latéral et le pied de page, formate les états et dates, charge les données, met à jour les éléments de la page et actualise l’affichage toutes les dix secondes. Il relie aussi les formulaires de parcelles, zones, missions et irrigation.

Les liens du menu sont définis par le tableau MENU en haut de app.js. Les identifiants HTML tels que missionForm, graph et historyTable relient chaque page au JavaScript : si un identifiant change, son utilisation dans le script doit être mise à jour aussi.

5. Données et stockage

js/data.js — données affichées

Définit DONNEES_DEMO, les événements, les parcelles et zones, les missions historiques et le dernier état illustratif du robot. Les valeurs de batterie, vitesse et position sont fictives. Aucun capteur réel n’est lu.

js/api.js — accès aux données

Malgré son nom, ce fichier n’effectue actuellement aucun appel HTTP ou MQTT. Ses fonctions charger... exposent les données de data.js. Les modifications sont conservées dans le localStorage du navigateur sous les clés :

  • roboagri.parcelles
  • roboagri.zones
  • roboagri.missions
  • roboagri.configurations-irrigation

Ces données restent dans le profil du navigateur et ne sont pas envoyées à un serveur. Effacer les données du site peut les supprimer.

7. Parcours des formulaires

  • Parcelles et zones : app.js lit les formulaires, appelle enregistrerParcelle ou enregistrerZone dans api.js, puis actualise l’affichage.
  • Missions : l’heure et l’ordre sélectionné sont transformés en objet. enregistrerMission crée un identifiant et ajoute l’objet au localStorage.
  • Irrigation : la page consulte les événements d’arrosage, leur durée, leur volume et les mesures associées. Elle ne configure pas de seuil et ne décide pas si un arrosage est nécessaire.

8. Limites avant un branchement au robot

Le formulaire de mission ne transmet pas de mission à un ESP32. Il enregistre seulement une préparation dans le navigateur. Les missions, états, mesures, incidents, batterie et événements d’irrigation affichés sont simulés. Cette interface n’est pas connectée au robot et n’envoie aucune configuration de seuil.

Pour connecter le système, il faudra définir une interface réelle avec l’ESP32, généralement par un backend ou un broker, ainsi qu’un format de mission, des accusés de réception, des états et des règles de validation. Le capteur fournit la mesure ; le contrôleur, par exemple l’ESP32, applique le seuil configuré dans son programme et pilote la pompe. L’application pourra ensuite consulter les mesures et résultats transmis. Cette interface n’est pas un système de commande opérationnel.

9. Feuille de style

css/style.css définit les couleurs dans :root, les composants communs (navigation, cartes, états, tableaux, formulaires), la grille du tableau de bord, les styles de l’accueil et les adaptations mobile.

Les animations utilisent des transitions et des media queries. La règle prefers-reduced-motion réduit les mouvements si l’utilisateur le demande. Les couleurs de marque principales sont --vf (vert forêt) et --vf2 (vert naturel).
