CHAPITRE 01

Avant de commencer

Du capteur à la décision d’arroser : comprendre les données, les règles et les limites du système.

Cette documentation décrit le dépôt RoboAgri-Kin, confirmé comme le projet à analyser. Elle est fondée sur les fichiers locaux examinés le 18 novembre 2026. Les comportements décrits viennent du code exécutable ; les anciens README ne font pas autorité lorsqu’ils le contredisent.

Ce que le système fait. Il organise les parcelles et les missions d’un robot agricole, reçoit des mesures d’humidité, les convertit grâce à un étalonnage et propose une irrigation. Un humain autorise l’opération ; le robot rapporte ensuite son résultat.

Il s’agit d’un monolithe Django : une application serveur, plusieurs modules métier, une base SQLite et une API REST. Aucun moteur d’intelligence artificielle, broker MQTT, ordonnanceur de tâches ou firmware ESP32 n’est implémenté dans le périmètre Python examiné. Le dossier robot/ ne contient que .gitkeep.

Parcours conseillé : lire l’architecture, les relations, puis les trois parcours métier. Les développeurs peuvent ensuite ouvrir le dictionnaire de tous les champs et l’explorateur de code. Les responsables de projet trouveront les écarts et travaux restants dans « Limites et priorités ».

La documentation fonctionne hors ligne, sans serveur, bibliothèque externe ni appel à la base. Le code intégré est un instantané ; la clé secrète Django a été retirée. Aucun mot de passe de compte, jeton de robot ou contenu de session n’a été extrait de la base.

CHAPITRE 02

Architecture et trajet d’une requête

Navigateur
session + CSRF→Routes Django
API / pages→Vues et serializers
identité, droits, entrée→Services métier
règles et transactions→ORM → SQLite
persistance

Le robot utilise les mêmes routes serveur sous /api/robot/, avec une authentification distincte. Une requête arrive dans roboagri_config/urls.py, puis dans api/urls.py. DRF authentifie l’appelant, contrôle ses droits, puis exécute la vue. Un serializer transforme et valide les données JSON. Les opérations métier complexes appellent un service ; les CRUD simples utilisent directement le ModelViewSet et l’ORM.

L’ORM traduit les opérations Python en requêtes SQL. La réponse repasse par un serializer pour obtenir un JSON. Les exceptions métier prévues sont souvent converties en erreurs HTTP 400. Les erreurs non traitées peuvent produire une erreur serveur : toute erreur n’est donc pas automatiquement normalisée.

Comment lire un module Django

models.py définit le stockage ; services.py exprime les règles ; admin.py configure l’administration ; apps.py déclare l’application ; migrations/ versionne le schéma ; tests.py vérifie certains scénarios. Les views.py des cinq domaines sont des squelettes : les véritables vues API sont centralisées dans api/views.py. Les fichiers __init__.py marquent les paquets Python.

CHAPITRE 03

Base de données : relations et garanties

Le serveur utilise backend/db.sqlite3. Les 12 modèles métier ont chacun une table. Django ajoute ses tables de comptes, groupes, permissions, sessions, journal d’administration et migrations. Les identifiants id sont des clés primaires numériques automatiques.

Une mesure conserve simultanément sa zone, sa mission et son robot : les services doivent vérifier la cohérence de ces liens, car une clé étrangère garantit surtout l’existence de la cible.

Suppression et historique

Les relations métier utilisent presque toutes PROTECT : Django empêche la suppression d’une cible encore référencée. La relation étape → mission utilise CASCADE : supprimer une mission supprimable entraîne ses étapes. Une mission déjà référencée par une mesure reste protégée. Ces règles de suppression sont prises en charge par Django et ne doivent pas être assimilées à toutes les actions SQL natives possibles.

null=True permet une valeur SQL NULL ; blank=True autorise un champ vide dans la validation. DecimalField représente les valeurs avec précision décimale ; max_digits inclut les décimales. Les validateurs Python ne sont pas tous des contraintes SQL et objects.create() n’appelle pas automatiquement full_clean().

Transactions et accès concurrents

Les services utilisent transaction.atomic pour valider ou annuler ensemble plusieurs écritures. Certains relisent l’objet avec select_for_update(). Sur SQLite, cela ne fournit pas le verrouillage de ligne attendu sur un moteur qui le supporte ; les tests séquentiels ne prouvent donc pas la résistance à des appels simultanés. Les index uniques restent importants.

Évolution du schéma

Les migrations initiales créent les tables. La deuxième migration d’incidents ajoute message_id ; celle d’irrigation ajoute l’unicité de recommandation. Ordre des dépendances : parcelles → missions → mesures → irrigation/incidents, avec dépendance au modèle utilisateur. Toutes les migrations existantes sont marquées appliquées dans la base observée. Un écart supplémentaire de validation sur Parcelle.superficie est détaillé dans les contrôles.

CHAPITRE 04

Connexion, rôles et sécurité des accès

Humain : session Django

  1. Le navigateur ouvre /connexion/ : LoginView rend le formulaire avec CSRF.
  2. Le formulaire POST valide les identifiants et ouvre une session. Le cookie de session accompagne les requêtes suivantes.
  3. Une page protégée est servie par page_frontend. Un visiteur anonyme est redirigé vers la connexion.
  4. GET /api/auth/me/ retourne le profil et les groupes. Les écritures fetch incluent X-CSRFToken, lu depuis le cookie csrftoken.
  5. La déconnexion passe par POST avec CSRF sur /deconnexion/.

Les réglages actuels n’activent que SessionAuthentication pour l’API humaine. Ni Basic Auth ni JWT ne sont configurés. Le frontend et l’API partagent la même origine ; aucun middleware CORS n’est configuré.

Les permissions vérifient les noms exacts des groupes. Être dans « Administrateur » ne donne pas automatiquement accès à /admin/ : l’administration Django utilise notamment is_staff et ses permissions propres. creer_groupes crée les groupes, sans leur attribuer des permissions de modèles. creer_compte crée ou met à jour un mot de passe et ajoute le groupe ; il ne retire pas les anciens groupes et ne valide pas explicitement la force du mot de passe.

Robot : une identité séparée

X-Robot-Id contient l’UUID public du robot et X-Robot-Token son secret. L’authentificateur charge le robot, compare le secret avec check_password et construit un RobotPrincipal. Ce principal est authentifié mais n’est pas un utilisateur Django. Les routes humaines le refusent ; les routes robot exigent précisément ce type de principal.

Le jeton est enregistré avec make_password dans jeton_hash, jamais renvoyé par RobotSerializer. Le formulaire admin exige un jeton à la création et permet son remplacement. À l’inverse, le CRUD API des robots ne propose aucun champ jeton : créer un robot par cette API ne suffit pas à le rendre authentifiable.

Les routes robot limitent les lectures de missions et de commandes au robot connecté. Une mesure entrante doit citer son propre id numérique et une de ses missions. Cette protection ne règle pas tous les cas de déduplication globale, détaillés plus loin.

CHAPITRE 05

Parcours 1 — préparer et lancer une mission

  1. Préparer les références : créer culture, parcelle, zones et robot ; configurer son jeton par l’administration. Son état doit être connecte pour l’envoi.
  2. Créer la mission : POST sur /api/missions/ avec robot, date_mission, éventuellement description et une liste ordonnée zones. Si zones est fournie, la mission et ses étapes sont créées dans une transaction unique. creer_mission attribue le créateur connecté ; statut initial planifiee et transmission en_attente.
  3. Ajouter les étapes : POST sur /api/etapes/ avec mission, zone, ordre et description facultative. ajouter_etape refuse une mission non planifiée.
  4. Envoyer : POST sur /api/missions/{id}/envoyer/. Le service exige au moins quatre étapes, un robot déclaré connecté et aucune autre mission en cours pour lui.
  5. Consulter côté robot : GET /api/robot/missions/ puis éventuellement la route des étapes. La liste comprend toutes ses missions, sans filtrage d’état ; le firmware devra interpréter etat_transmission.
  6. Accuser réception : POST sur /api/robot/missions/{id}/accuse/. Une transmission envoyee devient accusee_reception, le statut passe à en_cours et date_debut est enregistré.
« Envoyer » est une transition en base. Le service n’ouvre pas une connexion vers l’adresse IP du robot. Il prépare un état que le robot vient consulter en HTTP. Aucun dispositif de polling du firmware n’est fourni ici.

Deux états, deux significations

statut décrit l’exécution métier ; etat_transmission décrit la communication. Une perte de communication positionne non_confirmee mais ne termine pas la mission.

CHAPITRE 06

Parcours 2 — recevoir et comprendre une mesure

Le robot envoie les six champs ci-dessous. Les nombres et UUID sont des exemples fictifs ; les références doivent exister dans la base du serveur.

POST /api/robot/mesures/
X-Robot-Id: UUID_PUBLIC_DU_ROBOT
X-Robot-Token: SECRET_DU_ROBOT
Content-Type: application/json

{
  "robot": 1,
  "mission": 1,
  "zone": 1,
  "valeur_brute": "100.00",
  "date_heure": "2026-11-18T09:00:00Z",
  "message_id": "00000000-0000-4000-8000-000000000001"
}
  1. RobotMesureInputSerializer valide les clés étrangères, le nombre décimal, la date et l’UUID. La vue compare le robot et le propriétaire de la mission à l’identité authentifiée.
  2. recevoir_mesure normalise l’UUID. Si une mesure existe avec ce message_id, il renvoie l’ancienne sans la recalculer, même si le contenu a changé.
  3. Le service exige une date consciente du fuseau. Il sait refuser un âge maximal, mais la route HTTP ne fournit pas ce paramètre : aucune expiration n’est donc appliquée par ce chemin.
  4. Il crée une mesure reçue puis vérifie l’accord robot/mission, la présence de la zone dans les étapes et l’existence d’un étalonnage actif.
  5. Une erreur métier de validation conserve la mesure avec invalide, son motif, une humidité non calculée et un incident mesure_invalide. Elle ne produit pas de recommandation.
  6. Sinon, il calcule l’humidité, marque la mesure valide et appelle immédiatement l’analyse d’irrigation dans la transaction.

La formule réellement implémentée

humidité = (valeur_brute − minimum) × 100 / (maximum − minimum)
Exemple : (100 − 0) × 100 / (1000 − 0) = 10,00 %

La valeur brute doit appartenir à la plage fermée [minimum, maximum]. Le résultat est arrondi avec Decimal à deux décimales. La formule est croissante : elle ne modélise pas automatiquement un capteur dont la réponse diminue lorsque l’humidité augmente. Aucun traitement de température, correction de sol ou moyenne temporelle n’est présent.

Réponse et répétition réseau

La réponse contient mesure et recommandation_id. Le premier enregistrement retourne HTTP 201, même si la mesure a été conservée invalide. Un doublon retourne 200 et recommandation_id: null, y compris si la première mesure avait généré une recommandation. Il faut lire les champs métier, pas seulement le code HTTP.

Le service n’exige pas une mission en_cours et n’interdit pas explicitement une date future. Le test de déduplication a lieu avant les validations internes : son périmètre global mérite un durcissement.

CHAPITRE 07

Parcours 3 — de la recommandation au résultat

Mesure valide→Humidité < minimum→Recommandation→Autorisation humaine→Commande consultable→Résultat robot

1. Analyse automatique

analyser_mesure_pour_irrigation refuse une mesure invalide. Sans seuil actif, il crée un incident seuil_absent. Si l’humidité est supérieure ou égale au minimum, il ne recommande rien. Sinon, get_or_create crée ou retrouve une recommandation par mesure et zone, avec la durée maximale du seuil et une justification textuelle. Le maximum du seuil n’est pas utilisé dans la décision.

2. Autorisation humaine

POST /api/recommandations/{id}/autoriser/ avec {"duree_max": 10}. Le service vérifie le rôle, la validité de la mesure et une durée strictement positive ne dépassant pas celle recommandée. Il refuse une recommandation déjà autorisée. Il enregistre l’auteur et l’heure, puis crée une irrigation autorisee avec un UUID d’opération.

Le champ de justification d’opérations supplémentaires existe, mais une recommandation déjà autorisée est refusée avant la vérification de cette justification. Il ne faut donc pas présenter ce champ comme un mécanisme opérationnel de réautorisation.

3. Mise à disposition de la commande

POST /api/irrigations/{id}/envoyer/ exige l’état autorisee et le transforme en commande_envoyee. GET /api/robot/irrigations/ retourne uniquement ces commandes, filtrées par le robot de la mesure source.

4. Confirmation

POST /api/robot/irrigations/{id}/resultat/ reçoit par exemple {"succes": true, "duree_reelle": 8, "volume": "1.20"}. L’identifiant d’URL est l’id numérique, pas operation_id. Le serveur exige une commande envoyée ; pour un succès, la durée réelle doit être présente et ne pas dépasser la durée autorisée. Un échec crée un incident irrigation_echec. Le volume est stocké, sans calcul automatique ; son unité n’est pas définie explicitement par le modèle.

5. Absence de confirmation

signaler_irrigation_non_confirmee transforme une commande envoyée en non_confirmee et crée un incident. Le champ de délai vaut 30 secondes par défaut, mais aucun ordonnanceur ne l’exploite automatiquement et aucune route ne déclenche ce service. Un résultat tardif sera refusé par le service normal puisqu’il exige commande_envoyee.

Une confirmation répétée après succès est également refusée : l’idempotence des mesures n’est pas implémentée pour les résultats d’irrigation. Aucun code Python ne coupe physiquement une pompe ; cette responsabilité doit être réalisée dans le firmware.

Champs modifiables et champs calculés

Les serializers de culture, parcelle et zone exposent tous les champs, avec id automatiquement en lecture seule. Seuil et Etalonnage protègent leurs dates de création. Robot protège identifiant et derniere_connexion, omet jeton_hash et laisse modifier etat_connexion. Mission protège createur, statut, transmission et dates réelles ; les étapes imbriquées sont en lecture seule. EtapeMission protège statut et dates réelles. Les recommandations et irrigations sont exposées par des ViewSets en lecture seule, complétés par les actions métier POST.

MesureSerializer sait rendre une mesure, mais aucun routeur /api/mesures/ humain n’est enregistré. /api/historique/, /api/robot/etat/ et /api/configurations-irrigation/ n’existent pas dans les routes, Ces données sont maintenant consultables via GET /api/supervision/ pour les opérateurs et administrateurs.

Interpréter les erreurs

400 : données rejetées ou erreur métier convertie en ValidationError. 403 : absence de session, rôle insuffisant ou authentification robot refusée dans les cas couverts par les tests. 404 : ressource absente ou inaccessible au robot. 405 : méthode non autorisée. 500 : défaut non géré possible. Ne pas supposer que toutes les erreurs d’authentification produisent 401.

Le dashboard renvoie missions_par_statut (liste statut/total), incidents_ouverts et irrigations_non_confirmees. Il ne calcule ni tendance d’humidité ni consommation d’eau. Le rapport tente de réutiliser la vue dashboard décorée ; ce point figure dans les limites.

CHAPITRE 09

27

30    """

32    if not etalonnage.valeur_min <= valeur_brute <= etalonnage.valeur_max:

Glossaire et lecture critique

TermeExplication
API RESTInterface HTTP qui expose des ressources et des actions en JSON.
CRUDCréer, lire, modifier et supprimer une ressource.
ORMCouche Python qui manipule des modèles et produit des requêtes SQL.
SerializerConvertisseur et validateur entre JSON et objets Python/modèles.
ViewSetEnsemble de vues DRF pour une ressource, généralement liste, détail et mutations.
Clé étrangèreLien vers la clé primaire d’un autre enregistrement.
MigrationÉtape versionnée d’évolution du schéma de données.
Transaction atomiqueGroupe d’écritures validé ensemble ou annulé en cas d’exception.
IdempotenceUn même message répété ne produit pas une deuxième opération métier.
CSRFProtection des requêtes d’écriture faites avec une session de navigateur.
HachageTransformation à sens unique permettant de vérifier un secret sans le stocker en clair.
PollingLe client interroge périodiquement le serveur pour récupérer les commandes.
Service métierFonction qui applique une règle du domaine indépendamment du format HTTP.
Constat statiqueConclusion tirée du code, à distinguer d’un scénario effectivement exécuté.

Pour modifier ce système, commencer par formuler la règle métier, choisir le niveau où elle doit être garantie (serializer, service, modèle ou base), puis vérifier tous les chemins d’écriture, y compris l’administration. Un champ dans un modèle ne signifie pas qu’un processus l’alimente ; une route ne signifie pas qu’un écran l’utilise ; un test passant ne signifie pas que le robot physique a exécuté l’action.
